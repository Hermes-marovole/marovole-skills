## TL;DR

- **核心定位**：Personal Agent 解决“一个人怎么用 AI 提效”，企业级 Agent OS 解决“几十上百人跨部门协作时，如何让人类和 Agent 在同一套业务台账与权限下串联工作流、沉淀组织资产”。
- **三层改造架构**：以 Hermes Agent 的推理循环与多 Profile 机制为内核，向上搭**共享业务工作区**（统一数据库消灭微信文档与口头通知），向下垫**企业级控制面板与权限网关**（RBAC/ABAC 校验、沙盒隔离、跨部门异步脱敏 A2A）。
- **六大开源选型拼装**：`LiteLLM / One API`（模型路由与分部门计费）+ `RAGFlow`（带权限标签的文档/纪要 RAG）+ `Supabase + NocoDB`（Postgres 行级权限 RLS + 零 Token 人工改表）+ `Casdoor`（对接飞书/企微的权限网关）+ `E2B`（外部文件清洗沙盒）+ `Ankole`（企业级多主体参考内核）。
- **可观测与任务状态机**：当自动化任务突破每日百条，必须在调度与业务层拆出 **8 态任务生命周期**（特别引入“结果待核实”强制 Agent 自验），并在监控面板将**完成证据、调度记录与业务结果分开记录**（原帖监控面板实测：216 项总任务 / 154 项 Agent 任务 / 56 项常驻服务 / 最近结果正常 75 项）。
- **晚间 Skill 蒸馏闭环**：下班后由专职 Skill Agent 汇总全员当日对话，提炼高频动作为版本化 `SKILL.md` 入库并统一下发，解决员工因上下文压缩变“智障”的抱怨。

### 导语与监控面板实证

过去的 4 个月，作者团队基于 Hermes 架构处理信息搜集、整理、汇报、统计、决策、信息流转及跨部门/跨企业协作，基于一台 Mac 电脑、几台外部服务器加 Hermes Agent，每天处理 200+ 项自动化任务。

**【配图 1 转录：Mac Workspace 任务监控大屏】**
- **设备信息**：`Studio.local`（`Darwin · 本机采集`，每 60 秒从本机读取监控快照自动刷新）
- **导航数据**：任务总览 `216` 项 ｜ 执行记录 `1397` 条 ｜ 硬盘空间
- **任务总数拆解（216 项）**：`5` 项数据同步 · `1` 项报表与通知 · `154` 项 Agent 任务 · `56` 项常驻服务
- **最近结果正常（75 项）**：底部关键设计说明——**“完成证据见详情；调度与业务分别记录”**。

### 一、技术选型：为什么是 Hermes？

Hermes Agent 自带 `MEMORY.md` 与 `USER.md` 持久化记忆、基于 `SKILL.md` 的技能自进化闭环、多平台统一网关（Telegram、Slack、飞书、Discord）以及 Cron 定时任务和子 Agent 并行调度能力。

但当把个人端 Agent 直接推向一家 300 人、横跨运营、采购、库存、仓库、定价、财务、销售、客服的公司时，单用户架构会顶不住。市面上多数方案只是把个人 Agent 套壳在不同场景执行简单任务，并非真正的企业级系统。

**【配图 2 转录：Hermes 企业级 OS Agent 架构】**
1. **多入口接入层**：飞书、Telegram、Slack、Discord、邮件、网页表单 → 统一流入中央层。
2. **中央 Hermes 企业级 OS Agent 层**：含**渠道路由、任务拆分、Agent 协同、权限控制**四大模块（不同入口内容先进入 Hermes，由系统统一识别、拆分与分发）。
3. **统一数据库底座**（与 Hermes 双向读写·统一数据流转）：沉淀**消息记录、业务状态、任务数据、知识沉淀**。
4. **业务部门读取与协作层**：销售部、运营部、财务部、采购部、客服部基于统一底座协同。

### 二、什么是真正的企业级 Agent OS？（六大前置要求）

**【配图 3 转录：企业级多 Agent 系统架构】**
- **顶部入口**：部门与角色入口（财务 / 销售 / 运营）→ 权限挂载 / 动态路由 → **多 Agent 控制中枢**（分组与权限控制、异步协作与校验、动态路由/权限挂载、安全沙盒与清洗）。
- **六大核心模块**：
  1. **权限以及隔离**：不能让每个 Agent 扫描本机或读取他人文件（防止销售看财务文件）。单纯靠提示词安全等级极低，必须从根源上对 Agent 分组、分权限，跨部门协作需校验后异步完成。
  2. **共享业务状态**：实时业务台账多渠道承接并共享，降低高频运营沟通成本。
  3. **组织记忆**：`RAG + Markdown` 结合，解决员工使用中因上下文压缩导致的记忆丢失，把常用 Skill、规则放在统一空间。
  4. **控制面板**：公司核心数据（GMV、密钥等）严格分级控制谁能看、谁能改；外部内容（邮件/表单/IM/网页）进入系统前先经过**沙盒隔离与清洗**。
  5. **权限挂载**：基于角色做动态路由（财务打开只看财务，销售打开看销售），且各自的 Agent **没有擅自更改自身权限、跨部门、随意产出子 Agent 的能力**。
  6. **资产沉淀**：模型供应商（Claude / DeepSeek / OpenAI）只是几个月内互相追平的 Token 燃料，随时按封控松紧和价格热切换；**只有运营数据、工作流和记忆才是越用越值钱的核心资产**。

### 三、基于 Hermes 的企业级改造架构

针对 Hermes 默认单用户 Profile 的局限，改造思路是：**在 Hermes 推理循环上方搭建共享业务工作区，在下方垫一层企业级控制面板和权限网关**。

**【配图 4 转录：三层改造架构】**
1. **权限分组与跨部门异步协作**：
   - 利用 Hermes 多 Profile 机制拆分为**个人 Agent**（面向张三、李四本人，绑定员工身份）与**部门 Agent**（销售部、采购部等，仅绑定群聊、**代码层严禁私聊**，各自拥有独立物理数据目录）。
   - **跨部门异步脱敏协作**：当销售需要财务核对一笔回款时，由控制面板验证权限请求，向财务部门 Agent 发起一条异步 Agent-to-Agent（A2A）任务；财务 Agent 在隔离环境中核对后，**仅把脱敏后的简单状态（回款 / 未回款）传回销售 Agent**。
2. **状态共享**：邮件、群聊退换货、制作流程、前端门店订单全部由 Agent 隐性提取，写入同一套后端数据库，消灭微信文档与口头通知。
3. **记忆分层（RAG + Markdown）**：
   - **Markdown**：存高频核心业务 SOP（供应商名录、报表处理与产出规则、信息查找路径）。体积可控、高度浓缩、可人工维护，干活时定向读取注入。
   - **RAG**：解决几百号人运行数月后的海量非结构化检索——① 历史群聊决策溯源（如“上个月 12 号采购和运营为什么临时把 A 供应商账期改成预付 30%？”）；② 几百份历史合同 PDF、客服客诉原话、周会原始纪要切片检索；③ 几个月前老员工处理过的低频棘手奇葩事件相似匹配复用。

### 四、落地实操：1 周跑通 2 个部门的 MVP 三步法

**第一步：搞一台服务器或 Mac**
- 原则：服务器只跑网关、数据库和沙盒调度，**不跑本地大模型权重**（推理全走外部 API，无需买昂贵 GPU）。

**【配图 5 转录：云服务器（海外） vs 本地 Mac 部署对比】**

| 对比维度 | 云服务器（海外：日本/新加坡） | 本地 Mac（本地办公室） |
|---|---|---|
| **主要优点** | 配置灵活，可随时升级、动态扩容 | 数据本地存储，隐私性和自主控制力强 |
| **主要缺点** | 需持续按年支付服务器租金 | 硬件配置固定，扩容需买新设备 |
| **部署成本** | 小型业务约 **¥2,000 - 5,000 / 年** | 一次性购买 Mac 硬件 |
| **网络成本** | 通常含基础公网带宽，超额另计 | 需独立网络，约 **¥2,000 / 月（≈ ¥24,000 / 年）** |
| **综合建议** | 优先海外云服务器；若数据本地化要求高，采用**「云端运行 Agent + 本地存储敏感数据」混合架构** |

**第二步：安装 Hermes Agent，建好角色 Profile**
- 安装：`curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash`
- **企业化目录物理拆分**：不共用默认主目录，按部门和员工建立独立 Profile 目录（如 `/data/hermes/dept/sales`、`/data/hermes/dept/finance`、`personal/zhangsan`），配合网关路由让部门 Agent 仅绑群聊、禁用私聊。

**第三步：接入必备的六大开源组件（配图 6 完整转录）**

| 所需能力 | 推荐开源项目 | GitHub 仓库地址 | 在这套 OS 里干什么用 |
|---|---|---|---|
| **模型路由与燃料切换** | **LiteLLM 或 One API** | `BerriAI/litellm` / `songquanpeng/one-api` | 统一接管 Claude、DeepSeek、GPT 等模型，支持限流、分部门额度统计与随时热切换（国内接飞书登录可用 One API） |
| **RAG 知识库引擎** | **RAGFlow** | `infiniflow/ragflow` | 专门啃几百份合同 PDF、复杂表格、会议纪要和历史群聊切片，自带版面解析与原文溯源，检索前可带部门权限标签过滤 |
| **共享业务台账 & 数据库** | **Supabase + NocoDB** | `supabase/supabase` + `nocodb/nocodb` | Supabase 提供 Postgres 底座与行级权限控制（RLS）；NocoDB 直接套在上面变成“自建版 Airtable”，让运营/财务能零 Token 手改单元格 |
| **身份认证与权限网关** | **Casdoor** | `casdoor/casdoor` | 开源单点登录与 RBAC/ABAC 权限中心，原生对接飞书/企业微信组织架构，管死“谁能看哪个目录、谁能调哪个 Agent” |
| **外部文件清洗沙盒** | **E2B（或轻量 Docker）** | `e2b-dev/e2b` | 外部发来的报价单、网页抓取和 Python/DuckDB 重计算全丢进零密钥微虚拟机或隔离容器跑，算完吐出干净结果即销毁 |
| **企业级多主体参考架构** | **Ankole** | `AgentBull/ankole` | 如果后续要自研控制面板、FUSE 权限挂载和异步 A2A 审批流，可以直接参考它的开源内核实现 |

### 五、如何实际推进业务？（四条筛选标准）

找部门负责人问两个问题：**日常工作中哪些动作每天重复执行 3 次以上？哪些事需要反复找人确认？**
典型摩擦案例：销售拿客户付款截图问财务到没到账 → 财务确认后通知仓库 → 仓库发现订单号不全又找回销售。每个人都没做错，但一笔订单来回传几遍。

切入 Workflow 的四条立项判据：
1. **是否频繁发生**
2. **是否值得做**
3. **能不能通过数据倒推**
4. **失败了哪个员工来接手（背锅/兜底责任人）**

此外，企业中层大量的“分析、判断、向上级汇整日报/周报”工作也可直接 Agent 化。

### 六、权限的具体设置 Demo（配图 7 转录）

通过中央**调度中间件（核验授权 · 限定数据范围 · 控制工具调用）**串联四层权限：
1. **01 员工身份**：认证与人员系统确认（`发起人` | `所属公司` | `当前岗位` | `临时授权`）。
2. **02 Agent 身份**：`销售 Agent` | `财务 Agent` 各有独立服务身份，代表已获授权的流程执行任务。
3. **03 工具权限**：**不让 Agent 直接连数据库裸查**，而是给它`业务工具接口 + 数据快照`（如订单汇款状态、当前任务进度），既控权又减轻数据库压力。
4. **04 子 Agent**：由中间件分派任务与权限（`限定数据范围` | `限定可用工具`），子 Agent 的每次工具调用仍须经中间件校验。

### 七、任务队列与 8 态生命周期（配图 8 转录）

日均任务上百条后，单环节报错会阻塞其他部门，必须为人类和 Agent 共同定义精细的任务状态机：
- **未结束状态（均可取消）**：
  - 主干流：`待处理` —(开始执行)→ `执行中` —(提交结果)→ **`结果待核实`** —(核实通过)→ `已完成`
  - 驳回环：`结果待核实` —(未通过，返回处理)→ `执行中`
  - 条件分支（按需进入，条件满足后返回`执行中`）：`待补充` ｜ `待审批` ｜ `待重试`
- **结束状态**：`已完成` ｜ `已取消`
- **设计精髓**：专门拆出**“结果待核实”**状态，是为了从状态机层面强制 Agent 知道自己提交后必须走验证闭环，而不是跑完脚本就自认成功。

### 八、Skill 的控制及夜间自动蒸馏更新

员工日常直接对话容易因上下文压缩后效果退化而抱怨 Agent 智障。解法是建一个**统一的企业大 Skill 仓库**：
- 白天：张三的销售 Agent 在对话中摸索出自动根据数据算报表的方法；
- 晚上下班后：一个专门的 **Skill Agent** 把张三、李四、王五全天的聊天内容汇总分类，自动提炼制作为标准 `SKILL.md`；
- 夜间提交 Git 仓库（带版本记录）并自动下发给所有相关 Agent 安装更新，形成组织经验的日更复利闭环。

## 我的吸收判断（12年 PM + 一线 FDE 视角对账）

### 1. 水分与真实边界审计（哪些是干货，哪些不能全信）
- **监控截图暴露出的真实通过率（75 / 216 = 34.7%）**：作者在正文吹“每天处理 200+ 项自动化任务，爽的一”，但配图 1 的 Mac 监控面板（`Studio.local`）诚实地显示：**任务总数 216 项（其中 154 项 Agent 任务、56 项常驻服务），但「最近结果正常」只有 75 项**。这恰恰印证了我们一贯的判断：**在真实企业环境里，把 200 个 Cron 跑起来很容易，难的是对抗上游接口变动、超时和脏数据**。作者在配图 1 写下的那句小字 **“完成证据见详情；调度与业务分别记录”**，与我们自己的 **“不信 `last_status`，判活只看产出文件 mtime + 内容完成证据”** 完全同源，这是只有真踩过百级 Cron 坑的人才会写出的细节。
- **海外专线成本估算偏高**：配图 5 将本地 Mac 的网络成本估算为“约 ¥2,000/月（¥24,000/年）”，这是按传统企业 SD-WAN 专线报价算的；实际中小团队用 Mac Studio 本地跑调度 + 独享海外固定 IP 节点分流 API 请求，网络成本不到其十分之一。
- **Ankole 尚属早期参考项目**：表里推荐的第 6 个项目 `AgentBull/ankole` 实测仅 **181 Stars**（2026 年 4 月建仓），虽然其“零 Token 确定性 Applet Actions + 审批卡片 + FUSE 权限挂载”架构设计很漂亮，但成熟度远不如前 5 个万星组件，只适合参考状态机与协议设计。

### 2. 对我们现有架构（灵知 AI / FDE 推广 / 个人母节点）的可复用能力
1. **「NocoDB + Postgres RLS」作为非技术同事的零 Token 共享验收台**：
   - 我们在带非技术同事用 AI 提效时，最烦的就是同事在群里用自然语言让 Agent 改某个状态（既费 Token 又容易改错行）。借鉴其 **Supabase + NocoDB** 方案：Agent 负责从邮件/飞书/微信隐性提取结构化字段入库，运营/财务同事直接在 NocoDB 网页表格里像改 Excel 一样点选状态、填审批结果（零 Token、100% 确定性），触发 Webhook 唤醒下一环节 Agent。
2. **「部门 Agent 仅绑群聊 + 代码层禁私聊 + 跨部门只回脱敏布尔/枚举状态」**：
   - 随着团队更多人接入 Hermes，单机共用 Profile 会带来凭证与财务数据越权风险。按 `/data/hermes/dept/<name>` 拆分物理 Profile，并在网关层硬编码**“部门 Agent 拒绝私聊、跨部门 A2A 请求只返回预设 Schema 的脱敏快照（如回款=已到账/未到账，隐藏具体流水金额）”**，比任何 System Prompt 里的“请勿泄露”都可靠。
3. **8 态任务队列中的「结果待核实（Pending Verification）」显式状态**：
   - 把我们的 Grounding / 事实核查门禁和 Kanban Worker 生命周期进一步显式化：任何 Agent 跑完任务只能把状态推到 `结果待核实`，必须由独立的确定性探针或审计 Subagent 校验“完成证据”通过后，才能流转至 `已完成`。
4. **「如何推进业务」的四问立项漏斗（特别是第 4 问）**：
   - 跟业务部门对齐需求时，直接套用他的 4 条立项硬标准：**① 每天是否重复 ≥3 次？② 是否值得做？③ 能否通过数据倒推？④ 失败了哪个具体员工来接手兜底？**——没有明确人类兜底人的自动化流程，一律不准上线。
