# X 账号全量语料拆解（一个账号的推文 + 回复 + 截图 → 行业判断报告）

触发：用户贴一条 X 链接或 @handle，说「分析这个博主所有关于 <某主题> 的推文」。这是账号级语料拆解，不是单条视频拆解——不要只 fxtwitter 抓那一条。

## 1. 取全量语料（含回复）
- 一次分页抓全 timeline（含 replies），落 `<handle>_all.json`，保留每条的 `in_reply_to_status_id`、`created_at`、`id`、图片 URL 列表。
- **回复必须配父帖再读**：博主自己发的主帖给的是方法论与结论密度，他在别人帖子下的回复才吐实操细节（门槛几天、账号怎么隔离、单价、用的什么模型、地区要不要改）。用 `in_reply_to_status_id` 批量反查父帖，配成 Q→A 对逐条读。只读主帖会漏掉一半以上的硬信息。
- 同一天连发的多条常是同一论证的续帖（作者用「1. / 2.」拆条发），按 id 顺序合并成一篇再读，别当成独立观点。
- 作者可能改过 handle：旧回复里的 `@旧handle` 就是曾用名，报告写「原号 @旧handle」，不要当成另一个人或另一批数据。
- 时间序排 + 按主题切段。主题密度决定报告章节，不按时间流水账写。

## 2. 截图是主证据：先拼「带标签联系表」再喂 vision
- 这类账号的硬数据几乎全在截图里（后台概览、对标频道页、转账、邮件通知）。先按推文把图片原图下全，存 `<tweet_id>_imgN.jpg`。
- **不要一张一张喂 vision**：用 ImageMagick 拼 2×2 联系表，每格顶部压一条黑底标签写源文件名（`<tweet_id>_imgN.jpg`），一次 vision 调用读 4 张截图。标签是必须的——它保证读到的数字能对回原帖。
  ```bash
  magick montage -label '%f' -pointsize 22 -background black -fill white \
    -tile 2x2 -geometry +4+4 a.jpg b.jpg c.jpg d.jpg sheet_01.jpg
  ```
  （`-label` 需要在每张输入前生效；不稳就直接给每张图先 `-set label`，或生成后按坐标贴字条。）
- 提问模板固定为：「逐格转写所有可见数字：播放/观看时长/订阅/估算收入/RPM/日期/频道名/视频标题/UI 文案」。写明**逐格**，否则 vision 只详述第一格、其余一笔带过。
- **一张联系表不超过 4 格**：格子越多单格分辨率越低，后台小字（RPM、日期、订阅数）开始读错；4 格是「省钱」与「读对」的平衡点。
- 结果按 `<tweet_id> → 读出的事实` 追加写进 workspace 里的 JSON/CSV，最后在代码里汇总排序，别靠记忆拼表。

## 3. 截图里的数字怎么用
- **自己算隐含 RPM**：`估算收入 ÷ 播放 × 1000`，写「隐含 RPM ≈ $X」，并注明「概览页反算，非后台 RPM 栏」。只有截图里真的出现 RPM 栏时才直接引用作者口径。
- 同一账号的隐含 RPM 会大幅跳动（同一人既能晒 $0.9 也能晒 $3.1）：地区分布、广告填充、以及「被判同质化的月份本来就没有收益」都会扭曲。**报告给区间，不给单点**，并把扭曲原因写出来。
- **主动标注截图瑕疵**：播放数旁的⚠️警示标、估算收入打码、只截峰值那两天、只截单条不截频道总账。这决定用户该信哪几个数。
- 「冷启动滞后爆款」（前 10 天几十播放、第 60 天才起量）单独列一条，它是判断「内容资产 vs 平台运气」的最佳样本。
- 作者晒的**转账截图**（卖号尾款等）说明变现不止广告分成，是矩阵运营的旁证，值得写。

## 4. 从截图反查作者身份与自有产品
- 截图里反复出现的浏览器扩展按钮、水印、导出面板（「添加到 XX」「XX 剪草稿」）通常就是**作者自己的产品**。拿这个名字去 web_search，常能命中站点 `/terms` 页，页内联系邮箱可与 X 身份对上——这是最省的身份闭环。
- 作者自称「开源了工作流」时，直接查仓库树 `curl -sL https://api.github.com/repos/<owner>/<repo>/git/trees/main?recursive=1` 确认技术栈、目录结构、是否真有代码与 license，别信「已开源」四个字。

## 5. 政策类论断必须打一手源
- 平台规则数字（收益门槛、分成方式、生效日）一律去官方博客/帮助中心核完再写；作者的中文翻译截图只当线索。
- 检索技巧：拿截图里的**英文原句片段 + 关键数字**去搜，能一次命中官方原文；核到了才写「经联网核验为官方原文」，核不到就标「作者转述」。

## 6. 报告骨架（这类交付的形状）
1. **画像与动作脉络**：入场时间、原号/现号、代表作与制作栈、自有工具/开源仓库。
2. **核心战略判断**：为什么换赛道、为什么选这个平台、对政策风险的判断——按论点分节，每节挂推文出处。
3. **数据表**：一行一个样本，列为「内容形态 / 截图实录数字 / 隐含 RPM 或备注」。
4. **平台政策与起号实操**：门槛、后台坑、地区、提现延迟。
5. **风控与矩阵观**：隔离清单、连坐风险、多号并行。
6. **方法论 + 外部标杆清单**：每个案例给频道名、形态、截图数据、可迁移点。
7. **客观评估**：先说可验证的真本事在哪，再写内在张力与幸存者偏差——典型张力是「他主推精品 X，但高频拆解的是低成本模板日更 Y」，两者的壁垒与抗同质化寿命完全不同，必须分开说。缺这一节等于替对方做广告。

## Pitfalls
- **别把截图里的频道当成作者自己的**：截图常是对标别人的频道，只有作者明说「这是我的」才算自证；否则一律写「对标样本」。
- 第三方工具的估算收益（某雷达标注「日入千刀」）不是后台读数，写「工具估算」，不要写成事实。
- 报告结尾不要附工具版本提示、升级提醒、浏览器插件更新这类噪音——用户没问。
