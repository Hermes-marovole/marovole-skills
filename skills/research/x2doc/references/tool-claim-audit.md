# 被推文吹爆的软件 / 仓库：能力声明的核对与取舍

触发：帖子里推荐一个软件、仓库或 CLI，并给出「内置 N 个工具」「什么都能干」「一键 XX」这类能力声明。目标是把营销话术换成可引用的事实，并给出本机要不要装的结论。

## 1. 先读官方自曝文档，再读 README 卖点

阅读顺序（后一项常推翻前一项）：

1. `README` 的 Status / IMPORTANT / Warning 块
2. `docs/STATUS.md`（做到哪一步、怎么验证的）
3. `docs/tool-status.md` / `docs/feature-status.md`（逐工具 Verified / Partial / Unverified 审计表）
4. `ROADMAP.md`、`docs/pitfalls.md`
5. `AGENTS.md` / `CONTRIBUTING.md`（工程纪律：禁 unsafe、禁 unwrap、外部进程统一封装——能看出这项目对自己代码的要求，报告里值得一条）

- 审计表里 `Unverified` 的行数是全篇最有价值的材料：它量化了「宣称的 N 个工具里有多少没在真机上跑过」。
- 源码/文档里出现 `simulated in source`、`not yet run live`、`built, not yet run live`、`early alpha` 这类措辞，原句抄进事实表，不译成「暂不支持」，也不淡化。
- 许可、建仓时间、最新 release tag、星数（写明快照截止日）一并进事实表：`gh api repos/<owner>/<repo> --jq '.spdx_id, .created_at, .stargazers_count'`。

## 2. 数量三处对账，不要挑一个

三个来源都要拿到：

| 来源 | 取法 | 常见问题 |
|---|---|---|
| 营销话术 / README | 原帖与 README 正文 | 取整、取最漂亮的口径（「320+」） |
| 仓库生成的清单 | `docs/tools.md` 之类 | 与 README 不同步，少几个 |
| 工具自己列出的清单 | `<cli> commands` / `--help` / `list` 子命令 / MCP `tools/list` | 才是真实的当前版本 |

三个数不一致就**并列写出、各带出处**（「README 说 320，其中引擎内 300；生成的清单是 302；实跑 `commands` 是 321」）。只取一个数是营销或抹黑，差在哪才是信息。

这条对所有「N 个工具 / 支持 N 种格式 / 覆盖 N 个平台 / 集成 N 个数据源」通用：数字进正文前，先跑一次列清单的命令。

**同一个安装文档内部的数字也会互相打架**：正文写「拷贝这 twelve 个目录」，紧接的列表列了 13 个，而 `find plugins -name SKILL.md | wc -l` 数出来 14。凡是散文里的数字一律当口误处理，真值只从文件系统数（`find <dir> -name SKILL.md | wc -l`、`find . -path '*/references/*.md' | wc -l`、`find . -path '*/scripts/*' -type f | wc -l`），报告里写「文档 X / 列表 Y / 实际 Z」三列并指出漏了哪个，别挑一个。

### 规模声明（「学了 N 个教程 / 训练了 N 篇论文」）查不到来源时

宣传「让 AI 看了约 1000 个 YouTube 教程」，仓库里却搜不到链接，不要直接写成造假：

1. `grep -riE "youtube.com|youtu.be|Source:|Sources:" <repo>` 数残留引用行，看它是零散还是彻底没有；
2. 再读它自己规定出处写法的规则文件（如 `references/tutorials-to-skill.md` 里「频道名与视频链接只出现在 `Source:` 行」那一节）——不少作者在公开版里**故意剥离署名与链接**，原文会直说「公开副本删掉这些行，学习过程留在私有，也免了来源之争」；
3. 结论写成「规模声明不可外部验证，且不可验证是仓库自己规定的」，并引那句原话。这比「疑似夸大」准确，也难被反驳。

能外部验证的替代证据是它留下的统计口径（例如「对 1,960 条科普 Shorts 与 2,589 条 30 秒 3D 短片做过播放量回归」）：这种数字照录并标注「它没有公开样本」，同一条回归里得出的反直觉结论（播放量差异主要来自发布年份、文案句式在新片里加成归零）往往比工具本身更值得写进报告。

## 3. 亲手跑一次被吹的那个动作

- 它说「默认安全 / 净室」：不带开关直接调受限工具，把结构化报错原文（`code`、`message`、`remediation`）抄进报告——报错就是证据，比转述政策强。
- 它说「零依赖解析」：拿本机现成的二进制或包跑一遍，报符号数、依赖数、耗时。
- 它说「自动验收」：读验收脚本的阈值（几档屏宽、采样几次、比什么指标），把阈值列成清单——这通常是最值得借的机制，比它的一百个工具都值钱。
- 实测只写自己真跑出来的数；作者自述的规格（体积、耗时、覆盖率）标「官方披露」。

## 4. 取舍：先问「本机是不是已经有了」

- 挂 MCP 之前先查已有插件与 MCP 服务器清单。已有插件覆盖同一能力（哪怕工具名不同）就不要为一个新工具把上百个工具塞进全局命名空间：工具名碰撞与每轮上下文膨胀的代价远大于收益。
- 一次性分析走 CLI 单次调用，用完即弃；只有每周都会用的能力才值得挂 MCP 或写进 skill。
- 报告里保留「本机集成状态」一列：已内置 / 已下载未挂载 / 不集成，并写理由。默认结论是借 2–3 个机制，不换栈、不重复集成。

## 5. 成稿角度：用它的自曝做反差

- 最稳的钩子是「它自己承认了什么」：N 个工具未验证、某模块源码是模拟的、构建强依赖某个已登录的第三方 CLI、C# 没有内置反编译器。这类反差有据可查，且天然对冲转发区的吹捧。
- 原帖评论区骂「垃圾」时不要选边：把骂声与官方审计表对上——用户按营销话术的预期去用，撞上的正是那些 `Unverified` 的行。
- 标题里的每个数字都要能在事实表查到；星数、天数这类快照值写清截止日。

## 6. 薄壳判定：营销仓在哪儿，执行仓在哪儿

「开源」「免费」「一句话全自动」「人工成本归零」是四句独立宣称，逐句验证，别当成一句话一起信。

**先看代码量，再看星数**：`find . -name '*.py' | wc -l` 为 0、整仓只有 Markdown 的 Skill 仓很常见。零行代码不等于骗人——它可能在调别的东西——但结论必须写成「它是 X 的薄壳」，并顺着它去找 X。

**顺着依赖找执行仓**：`grep -rE "https?://|subprocess|requests|httpx"` 看它请求谁；配置模块的 `DEFAULT_CONFIG` 常直接写着服务端地址和一个空的 key 字段。执行仓的星数通常只有营销仓的百分之几（壳是给人装 Agent 用的，传播力全在壳上），但真相全在执行仓里。同组织的兄弟仓一并扫：`curl -s "https://api.github.com/orgs/<org>/repos?per_page=100"` 按星数排序，星最少的那个往往就是真正的执行层。

**执行仓 `docs/` 里非工程角色的文档是最高价值材料**：运营、销售、客服、FinOps 手册常被 CI 从内部（飞书 / Notion）同步进公开仓。它们写给员工看，不是写给人看卖点：

- 服务上限的真实原因（「单批默认上限 5，约束来自测试人员单批审核工时随数量线性上升，不是 API rate limit」）；
- 对外话术与内部事实的落差（「客户问起为什么限 5，不要说 rate limit」「平台驳回 AI 一键生成时，主张产品本质是人工质保的服务交付」）；
- 成本结构里那项营销从不提的支出（人工核对人天）。

这类原句直接引用——它是全篇最硬的证据，也天然是反差选题。找法：`ls docs/`，文件名带 `runbook / playbook / finops / faq / batch / sales / ops` 的都读一遍。

**「一句话全自动」的判据是它自己的确认条款**：`grep -niE "confirm|approval|never auto|before submitting" SKILL.md`。若它写着「每个资源、每次提交都要用户明确批准，绝不自动选择、绝不自动提交」，那原帖的「甩一句话全包」就是错的；同时把这条确认机制记为可借项（写法见 `skill-authoring` 的 `references/agent-facing-skill-patterns.md`）。

**付费门**：要加客服微信、要发邮件到某个自有域名才能拿到 key、按字数或分钟扣点的，一律定性为「闭源商业 API 的薄壳客户端」，并列出计价表。「花销提前算得明白」不等于免费。

**数字打架时优先信 API 响应示例**：README 写 93、SKILL.md 写约 100、`references/resources.md` 贴的真实返回 JSON 写 `"total": 101` —— 以实际响应为准（那是接口真值），正文并列三个出处。

## 7. 反模式

- 把 README 的 slogan（"See how any…"、"anything"、"一键"）当事实引用。
- 把官方审计表当成作者的谦辞跳过——它是唯一能证明项目边界的公开材料。
- 只写能力不写前置条件（要用户自己的订阅额度、API key、付费档、本机已登录的编码 Agent）。
- 因为一个工具很火就建议换掉现有产线；用户偏好是现有 skill 能出活就直接复用。
- 把「开源」等同于「可本地跑」「免费」：先看代码量、执行仓、key 的获取方式，再下这三个结论。
- 只读营销仓的 README 就写结论，不翻执行仓 `docs/` 里同步进来的内部手册——那里才有服务上限和成本结构的真话。
