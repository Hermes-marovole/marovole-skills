# 厂商发布公告 / 版本升级稿的核查程序

适用：写「某产品发布 X 版本、新增 Y 能力」的短评、科普稿、评测稿；来源是厂商发布博客 + whats-new/release-notes 页 + 文档命令参考。这类稿件的失真有固定形状，review 报的错九成落在这五类里。

## 先分清三种口径，混用必被打回

| 口径 | 只能取自 | 能写的话 | 写成就错的话 |
|---|---|---|---|
| **文档口径**（能力存在） | 命令参考 / API 文档逐条 | 「CLI 提供 `recompile`、`test` 命令」 | 「这是本次版本专门修的痛点」 |
| **版本口径**（本次发布改了什么） | release notes 的条目列表 | 「本次版本把列表输出统一成 JSON」 | 把文档里早就有的能力算进本次更新 |
| **遥测口径**（用了多少） | 厂商公布的统计快照 + 该快照的公布日 | 「据 <公告日> 官方公布，自 <起算日> 以来…」 | 把快照日当统计截止日，或把起算日当产品上线日 |

## 五类固定失真

1. **累计统计被挂到错误的窗口**。原文 `Since July 20, more than N logged-in users have run more than M commands` 只说明「从 7 月 20 日起累计到今天这么多」，不说明 7 月 20 日是公测/上线日，也不说明数字截止到公告当天。写法照抄原文的窗口词：「据 <公告日> 官方博客公布的数据，自 <起算日> 以来，超过 N 名登录用户跑了 M 次」。
2. **两套快照的数字被并列成同一时段**。厂商在不同时点各发过一个快照（早期复盘页给的是「7 月 20 日–某日」的另一组用户数/事件数），两组数字各自绑定自己的统计窗口。分别标注窗口与出处，别把 A 快照的用户用量和 B 快照的占比写进同一句「这个期间」。
3. **百分比把残差抹掉**。原文 `人 0.2%、CI 0.3%、约 98% 来自自动化、另有小部分不属于这三类` 是四段，不是「剩下的全是自动化」。写「约 98% 来自 X，其余为一小部分未归类运行」，不写「剩下的全部/全是」。
4. **替厂商补一块原文没有的能力边界**。「连破坏性操作和只读查询都帮你标好了边界」这类对称性描述最容易被脑补出来——文档只写了该命令存在、可配置客户端，就只写这些。
5. **把「Today」当成日期证据**。发布博客常写 `Today at Unite <城市>` 而不给日期；明确日期在 whats-new / release-notes 页的页眉（`Reviewed <Mon DD, YYYY>` 或 `1.0.0 shipped <Mon DD>`）。两条来源都要进台账：博客给引语，release 页给日期，并在 `derived` 里收一条「<中文日期> ← <英文原文日期>」，否则 `check` 报「确认不了发布日期」。

## 交稿前自查顺序

1. 每个数字后面问一句「它绑的是哪个快照、哪个窗口」，把窗口词写进句子。
2. 全文搜「全部、所有、全是、剩下的、整整、专门、为此」——它们几乎都把原文强度拔高了一档。
3. 涉及「本次版本」的句子，回 release notes 条目列表逐条对：条目里没有的，降级成文档口径（「CLI 提供 X」），不写「本次修复」。
4. 缓存一份「口径表」：同一批数字在长文、短视频口播、屏幕大字、X 帖里逐字一致；改口径时四处一起改。
