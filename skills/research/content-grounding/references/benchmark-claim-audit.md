# 评测表 / 渠道对比榜 / 论文消融的事实核查

适用：供应商对比榜（同一模型不同渠道成功率、tps、价格）、leaderboard、eval 报告、"某来源被降智"这类帖子的真伪核查与转述；以及拆论文时的消融表、相关系数表、达成率表。

## 0. 先把测试条件抄成一行

并发数｜每档尝试次数｜墙钟或超时｜harness（工具集、system prompt、max_tokens、reasoning 档位）｜样本量｜采样日期。

这一行是后面每个数字的定语。写稿时数字要么带它，要么不许出现在结论句里。缺其中某项（常见：没写用的是哪档套餐、没写是否钉到具体 tag）就进「没证实」清单，不要默认最有利的假设。

## 1. 列语义：最容易读错的六列

| 列 | 衡量的是 | 常见误读 |
|---|---|---|
| 输出速度 tok/s | 全表条件下、单个 worker 的速度 | "这家的速度" → 实为并发排队后的残余速度 |
| 成功率 | 模型 + 容量 + 墙钟三者混合 | "模型能力" |
| 超时率 / out of time | 到墙钟时还没跑完 | 与「答错」混为一谈 |
| Failures | 只记服务端失败，且很多榜单明确写"不重试" | 与限流同源 |
| cost per token | 单价 | 与 cost per solve 混用 |
| cost per solve / per task | 含失败与低成功率的摊薄成本 | 反推成"更便宜" |

判读规则：一个渠道在 x10 并发下崩掉，先查它的并发额度与队列规则原文（服务商 FAQ 通常明写"超出套餐并发的请求排队，队列满才拒绝"）；3 路额度打 10 路，剩下 7 路排队的时间全进墙钟——这是配置效应，不是能力效应。

## 2. 计数与聚合：只用结构化行

- "N of M 落在某区间"必须解析源表格的**行**，用代码统计并打印分布（含 n/a 行、含参考端点/参考柱），不要从条形图的文字流、图例、截图或长段拼接正文里数——从这些源数会稳定差一。
- 排名要写并列（三家都是 18/40 就写并列第一），区间下端要看全表（表里有 0 分的，最低值就不是 12.5%）。
- 派生数字（倍率、p 值、均值、差值）全部重算并在稿末留算式；"p≈0.0026"这种要能复现。

### 2.1 对比两组条件，聚合方式必须同口径

拿「A 条件下表现最好的那一组」去对「B 条件下多组的平均值」，是拆论文/评测时最常见的一次口径事故，且几乎总把差距夸大成另一种事实。规则：**先确认两边各自怎么聚合（裸均值 / 加权 / 最优单组 / 多组平均 / 中位数），再决定写哪一对数**；句中把聚合方式写出来（「6 组锚点平均下」「单组最优时」），或两边统一成同一种再对比。两种口径都值得写时并列成一句，不要只留更惊人的那个。同一指标在正文表与附表里数字略有差异（如 $4.0\pm0.1$ vs $3.94\pm0.08$ / $4.09\pm0.07$）时，标明取自哪一处，不要把两处混着用。

### 2.2 「达成率 / 相对上限」的 100% 通常是作者自建的经验基准

论文里的「相关达成率 90%」这类百分比，分母往往不是理论满分 1.0，而是作者把人类样本随机拆半、重复上千次得到的重测信度上限。写成「达到理论上限的 90%」是失真；要写清分母是怎么来的（「相对人类重测信度基准的达成率」）。读不懂分母就先不写这个百分数，只写原始相关系数与样本量。

## 3. 归因禁区

- 两列加不平（超时数 + 解决数 > 尝试数）时，写"两列口径重叠、测试方未说明"，不要补机制。
- 推机制前搜否定词：`never retried` / `single run` / `not a statistical pass@k` / `not calibrated`。源文否定过的机制，一句都不能写。
- n=1 的多渠道对比图只当轶事；本地只抓到图片占位、没有可逐字核对的文本时，不引用图里的具体数字，只写发帖人的定性表述并标明 n=1。
- 社区体感帖（tps、额度、月用量）是可引的一手体验，但必须写明是谁、在哪、什么套餐；不同人对同一渠道给出相反体感，说明条件不同，不是有人撒谎——把条件差异写出来。

## 4. 标题、KPI 与选型结论

- 标题不得断言正文说无法证实的前提。源页写 "providers say it's the same model"，标题就不能写"同一份权重"；正文既然列了"无法证明逐比特一致"，标题就得跟着降级（"都说自己在跑 X"）。
- KPI 卡与结论里的每个形容词回表找列："又便宜又能打"要同时过单价列和 per-solve 列；"最快"要看是全表还是单 worker；"几乎不影响"要有区间数字。
- 选型建议必须带适用条件。不带条件的结论会被用户的第一手经验直接推翻，而推翻之后要改的不只是一个句子——标题、KPI、表头、结论四处都绑着同一个前提，改口径时四处一起改，并升版本号（旧版留在同目录）。

## 5. 自证段落

报告里出现"我本机路由是 X""我实测 Y"这类段落时，要么标明"来自本地配置/个人实测，不在来源台账内"，要么移出报告只留在对话里。混进台账体系会让整篇的可复核性打折。

## 6. 独立核查派单模板

```
对象：<成稿路径>；原文目录：<evidence 目录>
逐句输出四列：原文句子（可截关键短语）｜判定（完全准确/措辞轻微偏差/事实错误/原文无依据）｜依据（文件名+原句片段）｜可直接替换的改法
必须点名的必查项：
1. 所有 N/M 计数与排名：用代码解析源表格重算，禁止肉眼读数与图例
2. 派生算术：倍率、p 值、均值，给算式
3. 标题与 KPI 是否断言了正文列为未证实的前提
4. 结论里每个定性形容词靠哪一列支撑
5. 机制归因是否被源文明文否定
6. n=1 或单场对比是否被写成规律
7. 两组对比的聚合方式是否同口径（最优对平均、加权对裸均值）
最后给一段总评：能否交付、必须先改哪几条（按 P0/P1 排序）。
```

核查回来的判定要自己回原文验一遍再改——subagent 的结论同样是自述，它说"原文是 24 个"，就去解析一遍行确认。
