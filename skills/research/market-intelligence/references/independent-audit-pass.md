# 交付前独立审计（第二模型交叉核查）

写报告的模型审不出自己的错：它会把当初的错误假设再复述一遍，看起来像「已核对」。定稿前必须换一个模型家族当审计员，并且喂给它**原文证据**而不是结论。

## 什么时候跑

- 任何带逐条 `[n]` 引用、要交给外部决策者（投资、采购、竞品对策）的深度报告。
- 用户问「有没有做过核实」时，默认答案是「没有」——不要口头保证已核对，直接补跑这一轮。
- 用户点名某个模型（如「派 subagent 用 Grok 审」）时照做，并把模型名写进审计文件标题，便于日后追溯是谁审的。

## 输入怎么组

1. 报告全文按页切：`pdftotext report.pdf -` 的输出用 `\x0c` 分页，得到逐页文本数组；每页带 `【Page N】` 前缀，审计意见才能精确到页。
2. 证据：读 `ledger.json` 的 `sources` 数组 + 同目录 `ev_<id>.txt` 原始抓取内容。
3. **只附该页段实际出现的 `[n]` 对应证据**：用正则从页段抽 `\[(\d+)\]`，再按 id 取证据。整篇报告 + 全量台账拼一个请求既超长又稀释注意力，审计员会跑去审无关章节。

## 调用方式

```python
import json, urllib.request

# 必做：显式禁用代理。本机开着 Shadowrocket / Clash 时，HTTP(S)_PROXY / ALL_PROXY
# 会让发往 127.0.0.1 的请求先交给代理再超时，报错位置永远是 socket.readline，
# 看起来像「网关慢」，实际请求根本没到 magpie。
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

payload = json.dumps({
    "model": "cursor/grok-4.7@500k",           # 先 GET /v1/models 确认存在；备用 cursor/grok-4.6
    "messages": [{"role": "user", "content": prompt}],
    "temperature": 0.1,
    "max_tokens": 700,
    "stream": True,                            # 长回复必须流式，非流式容易读超时
}).encode()
req = urllib.request.Request(
    "http://127.0.0.1:3425/v1/chat/completions",
    data=payload,
    headers={"Content-Type": "application/json",
             "Authorization": "Bearer magpie",
             "User-Agent": "hermes-agent"},   # 网关按 UA 路由，缺了会被拒或走错通道
)
with opener.open(req, timeout=35) as resp:     # 必须用 opener，不是 urllib.request.urlopen
    for raw in resp:
        line = raw.decode("utf-8", errors="ignore").strip()
        if line.startswith("data: ") and line != "data: [DONE]":
            delta = json.loads(line[6:])["choices"][0].get("delta", {}).get("content", "")
```

按 `data: ` 前缀逐行读 SSE，累加 `choices[0].delta.content`。

**返回 0 字符 = 推理 token 吃光了 `max_tokens`，不是网关坏了**：带思维链的模型（`factory/claude-sonnet-5-5` 一类）先烧 reasoning token 再吐正文，`max_tokens: 4096` 常被推理段吃干，`content` 回来是空串，脚本照样写出一个 0 字节的 `audit_partN.md`，跟「网关拒答」长得一模一样。判别只看一处：把响应里的 `usage` 打出来，`completion_tokens_details.reasoning_tokens` 接近 `max_tokens` 就是预算不足——实测一次审计 reasoning 7800 + 正文 3000，`max_tokens` 要提到 **16000**。非流式反而更好排障，因为它会老老实实把 `usage` 交回来。每段开跑先 `print(res.get("usage"))`，别等落了五个空文件才回头查。换模型时同理：`cursor/grok-4.7@500k` 在某段上 240s 没有任何产出，先降级 `cursor/grok-4.6` 或缩段，不要判定「审计这条路线不可行」。

**长度红线**：单次请求控制在 1 万字符以内（约 5–8 页正文 + 该段证据）。超过这个量级，实测 45s / 90s / 180s 三档超时全部打穿——不是网关慢，是一次性要生成的 token 太多。切段是唯一解。

**一次一段、落一个文件、顺序发，不要并发**：三个线程同时对同一网关流式请求，每个都在等生成，整体必然越过 `execute_code` 的 300s 墙，而且内核被杀时**已完成的那段内存结果也一起丢**。顺序跑、每段写完立刻落盘（`audit_part1.md`、`audit_part2.md`），中途超时只损失当前一段，前面的还在。也不要把它塞进 `terminal` 的 heredoc：同样的时长会撞 terminal 的 120s 默认超时，且没有任何中间产物。

## 并行方式

用 `delegate_task` 派 2–3 个 subagent，按「上卷产品篇 / 下卷商业篇」或按页段拆分。每个 child 的 `context` 必须自带：

- 报告 HTML 路径与台账路径（child 看不到你的对话）；
- 网关地址、Authorization 头、模型 id，以及「单次 prompt ≤ 4000 字符、socket timeout=25s、超时重试或降级 `cursor/grok-4.6`」的硬约束；
- 输出文件绝对路径（如 `audit_part1.md`）。

不要把「必须发现问题」写进 prompt——审计员会为了交差编问题。要求它区分「与证据冲突」和「证据未覆盖」两类，后者只在报告下了超出原文的断言时才算问题。也**不要**把你自己倾向的结论喂进去，否则它会附和。

## 五项核查清单（直接写进 prompt）

1. **数字与事实**：金额、百分比、日期、人名、公司全名、统一社会信用代码、法院案号、备案号、域名数量，逐条对原文；分母口径是否被偷换（部门收入 vs 集团总收入、注册用户 vs 付费用户）。
2. **引用编号**：正文 `[n]` 是否指向该结论真正的出处，有无错标、漏标、把 A 的引语挂给 B。
3. **外行可读性**：站在没有技术/金融背景的商业读者角度，哪一页哪句话仍是黑话、需要一句话解释。
4. **前后一致**：同一产品在不同页面的价格、积分、用户量、份额是否一致；不同章节的判断是否互相拆台。
5. **逐页修改建议**：精确到 `Page X` + 原句，方便直接改。

## 证据怎么裁：砍长度可以，砍到语义缺失就等于自己制造假问题

审计员判「证据未覆盖」的条目里，有一半是自己喂进去的截断造成的：把节点文本砍到前 30 行、把 JSON 过滤得只剩 `label`，审计员就看不到被砍掉的那句价格、那个按钮文案、那段回复的后两段，于是把**报告里真实存在的原文**标成「未核实」。

- **财报/年报这类长文本证据按「正文引到的那几个数字」开窗取片段，不要取开头 N 字符**：10-K 与年报正文前 900 字符通常是免责声明与董事长致辞，毛利率、销售费用明细、渠道收入全在几万字之后的表格里。拿开头片段去核，审计员会把正文里逐字准确的数字全判成「证据未覆盖」。做法：把正文引用的每个数值（`68.70%`、`2,681,965,763.16`、`74.41%`）拿去原文 `find`，每处取前 40 / 后 120 字符，用 ` // ` 拼成一条 excerpt；一个源只留命中的窗口，比整段头截断准得多。
- 每条被正文引用的证据，至少把**正文引到的那几句完整原文**原样带上，省略处写 `…(省略 N 行)`；宁可在同一段里少审两个 `[E*]`，也不要给残句。
- 审计员报「证据未覆盖」时，先回源文件 `grep` 一遍再处置：命中了是裁剪的锅（驳回并补证据重审），没命中才是报告真编了。
- 结构化节点（无障碍树 JSON）过滤时保留 `identifier`、`rect`、`label` 三个字段。正文里凡出现「逐字原文」「完整回复」字样的引语，必须整段带标点带编号一起喂，少一个序号就可能被正确地判成失真。

## 审计意见怎么读

- **默认假设审计员是对的**，尤其涉及算术与几何的条目：先自己重算一遍。`118px ÷ (540/160)` 手算成 21dp 而正确值是 35dp 这类错误，写的时候不会觉得有问题，只有换个人重算才暴露。
- **量出来的数字不要用形容词代替**：写「按钮拦腰截断月卡」之前，把两个 `rect` 的 y 区间相减，写重叠了多少 px。重叠 24px 和遮住整张卡片是两回事，夸张措辞是审计员最容易抓、也最伤可信度的一类。
- **推论与事实分层写**：`57 岁` 来自用户自述、界面上只有 `45 克` 目标、性别在节点里没有——三件事证据强度不同，合成一句「系统按 57 岁女性设定 45 克蛋白」就变成了已核实事实。凡是「界面事实 + 我的推断」拼起来的句子，推断部分要显式标成推断。
- **一份截图证明不了「没发生」**：不能凭「没看到回访入口」写「没有回访机制」，只能写「本次实测未见」。

## 验收与回改

- **child 的自报不算验收**：先确认 `audit_part*.md` 存在、非空、含页码定位，再说「审计已完成」。
- 逐条处置：接受 → 改正文并升版本号；驳回 → 记下理由（证据不足、审计员误读）。
- **一轮审计通常改掉两位数的事实条目**：不要指望一审即过。审计报告落盘后先按「与证据冲突 / 证据未覆盖 / 可读性」三栏拆开，冲突项逐条改原文，未覆盖项逐条回源 grep，可读性项批量替换术语。改完直接出 `v1.1`，不要在原文件上原地改——用户要能对比前后两版。
- 数字类问题要回改**证据台账**（`ledger.json` / `ev_*.txt`），只改正文会让下一轮 `sources.py verify` 与正文再次漂移。
- 改完重跑分页验收（`pdf-generation-fallbacks` 的 `verify_pdf_pagination.py`）：插入或删除一段就会推翻页码与目录。
