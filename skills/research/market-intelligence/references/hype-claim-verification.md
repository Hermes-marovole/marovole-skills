# 网传案例声称的分层核验（社媒帖子 / 播客 / 公众号）

用户丢来一条 X 帖、播客切片或公众号长文说「调研一下这个」时，十有八九是一条**没有具名主体认领的案例声称**：「某年营收几十亿的深圳大卖，用某个开源底座搭了 8 个 Agent 覆盖全链路，100 人研发」。这类调研有两种失败形态，都很致命：

- **替推主写通稿**：把「几十亿营收」「100 人研发」「效率提升 N 倍」当既定事实复述，读者拿它当决策依据。
- **过度证伪**：因为查不到具名公司就整条判为「营销吹牛」，把一个真实趋势一起扔掉。

正确做法是把**一条声称拆成三层**分别取证，并在开篇第一段交代清楚哪层证实、哪层无证。

## 一、三层核验表

| 层 | 要回答的问题 | 取证源（按效力排序） | 查不到时的写法 |
| :--- | :--- | :--- | :--- |
| **1. 个案主体** | 到底是哪家公司？它有没有公开说过？ | 上市公司季报/年报「管理层讨论与分析」、投资者关系活动记录表（巨潮、互动易）、业绩说明会实录、公司技术博客与招聘 JD、工商变更 | 「主体未具名，按匿名访谈处理」——只保留「推主自述」口径，不进结论 |
| **2. 行业大盘** | 同一类企业是不是真在做？有没有量化财务归因？ | 同赛道公司最新季报；券商研报里的一句归因（常比财报原文更直白）；行业白皮书给的渗透率与阶段分布 | 「行业层已证实 / 未证实」独立成句，不与个案混写 |
| **3. 生态落地** | 这个底座在该行业有没有真实二开？ | GitHub 搜「based on <底座名>」的二开发行版、垂直插件、awesome 列表；看 release 节奏、issue 活跃度、license、是否真有 release 物 | 「生态有/无公开落地物」；有仓库不等于有生产用户 |

**判据**：三层里只有第 2 层能证实时，结论句必须写成「趋势是真的，这家没有证据」，并放在第一段。用户要的是能不能据此下判断，不是一篇考据。

## 二、行业层的取证捷径（最常被跳过，也最有价值）

最硬的验证不在推文里，而在**同赛道上市公司的季报**。三个信号凑齐，就证明「行业确实在做，而且已进财务报表」，个案是否具名反而次要：

1. 营收增速与净利增速出现**大裂口**（利润暴涨而收入微降）；
2. 管理层把「AI 降本增效」写进业绩归因，且提到自研平台/模型名；
3. 销售/管理/研发**费用率同比同时下降**，或毛利率在降价环境中反而抬升。

配套技巧：

- 用「收入增速 vs 净利增速」的差值当入口，差值越大越可能在归因里出现 AI 与自动化。
- 券商研报的归因句往往一句话点破机制（「销售费用率下降主要系公司借助 AI 进行精细化管理」），比财报原文更好引用，但要标明这是券商判断。
- 行业白皮书给的是**阶段分布**（多少比例卖家用了工具、多少进阶到工作流或智能体），用来判断这套打法处在曲线的哪一段——这类数字最适合反驳「人人在用 AI 所以没差异」的结论。

## 三、开源底座的可用性审计（热度 ≠ 可上线）

盯着 Star 数和插件总数讲「生态爆发」是最常见的注水。判断一个开源 Agent 运行时/框架能不能进生产，看四件事：

1. **版本阶段声明**：README 或 release 页是否仍标 Developer Preview、是否明说会持续引入 breaking changes、是否声明未通过外部安全审计。
2. **安全记录**：未授权 RCE、沙箱逃逸、配置注入、read-only 逃逸这类问题，有没有对应已修复的版本号，还是只有「建议升级到最新版」。
3. **供应链**：插件生态有没有假冒/投毒插件导致主机被控的公开事件；有没有第三方扫描器与权限披露机制。
4. **控制面缺口**：企业要上线是否必须自建 RBAC 权限树、每会话隔离沙箱、密钥不进运行时、审计与回放、版本升级兼容——这层工作量决定它是「框架」还是「产品」。

**配套交付**：把这套判断落成一张**三条落地路线的选型矩阵**（买垂直 SaaS / 厂商驻场交付 / 开源自研 + 自建控制面），标注各自适用体量、真实优势、隐性成本与最短验证周期。矩阵比复述案例有用，也顺手回答了用户真正关心的问题「我该走哪条」。

## 四、交付结构（默认五段，顺序不要换）

1. **核真伪**：三层结论先行，明确写「哪层证实、哪层无证、口径是什么」。
2. **纵向拆解底座**：时间线（开源 → 桌面端 → 生态爆发 → 工程补课）+ 架构机制（为什么这类底座能被企业改造，而不是又一个套壳），并落到版本号与日期。
3. **横向行业对比**：同赛道公司或三种落地路线的对照表，每格带可查数字。
4. **去滤镜的深水区**：生产可用性、安全与供应链、数据基建与组织前提——这一段决定报告是不是软文。
5. **对用户的判断**：这套东西对他的业务/岗位意味着什么，哪层位置值钱、哪层正被挤压。

## 五、语言与口径规矩

- 推文里的体量、人数、效率倍数一律写成「推主自述」；能对上公开财报的才升级为数据。
- 不用「据知情人士」「业内人士透露」当证据；查不到就写查不到，并写清缺的是哪类信息。
- 不复述推文原句做开头，直接给判断；推文只作为「这条声称」的出处标一次。
- 报告结尾可以给下一步（出 HTML/PDF、展开某一段选型），但不要在正文里自称「已核验」「已交叉验证」——把证据摆出来即可。
