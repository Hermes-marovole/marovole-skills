# 从订阅额度反推可用 token 量

厂商只写「更大的周额度」「significantly higher quotas」，从不给 token 数。要把「$200/月能跑多少 token」答成一个可验证的数，靠三个输入和一个公式，不靠猜。

## 三个输入

1. **额度锚 Q（$/月）** — 必须是带日期的用户实测（「打满周限额烧了多少美元」），不是月费。月费与额度的比例通常 5–7×，且厂商会静默调整；第三方数据集的快照在额度被下调后仍显示旧值，可能高一倍。周额度 → 月：按 4.29 周（自然月），或按「一个月能吃几次周重置」算 5 次，两者都报。
2. **单价表** — input / cache read / cache write / output 四项都要，别只看 in/out。促销价必须带到期日：首发价与恢复价常常正好差一倍，而恢复后的价格又可能与竞品完全同价（结论从「便宜一半」变成「没差别」）。
3. **会话 token 配比** — agent 长会话里缓存读取占绝大多数。默认口径 `(cache_read, input, output) = (0.97, 0.025, 0.005)`。

## 公式

```
blend = 0.97·P_cache + 0.025·P_in + 0.005·P_out      # $/Mtok，混合价
tokens_per_month = Q / blend
```

97% 缓存是「长上下文、反复复用」的饱和口径。短会话、每次大量新读码时缓存率会掉到 60–80%，同样额度只拿到 1/3–1/2。所以报数必须带「按 97% 缓存」这句，并附敏感性表：

| 缓存率 | 同样额度拿到的 token |
|---|---|
| 97% | 1.00×（基准） |
| 80% | ≈0.5× |
| 60% | ≈0.3× |

## 双模型配对（lead + sidekick）

额度按各自单价扣（厂商原文：each model at its own per-token rate），所以：

```
blend_pair = s·blend_lead + (1-s)·blend_sidekick     # s = lead 的 token 占比
```

- 官方示例会话的 s 约 0.54，但它是按某一对模型调的，换 pair 会漂；报区间（0.4 / 0.54 / 0.6）比报单值诚实。
- sidekick 免费时 `blend_pair = s·blend_lead`，可用量放大 `1/s` 倍（约 1.85×）。
- **换 sidekick 之前先比 cache read 单价。** 缓存占九成时，cache read 贵的 sidekick 可能比 lead 还贵（cache read $0.30 vs $0.20 就足以让「便宜模型」变负收益）。厂商公布的「每任务省 X%」是拿高价 lead 测的，套到便宜 lead 上不成立。

## 交付口径

给三个数，缺一个用户就没法规划：

1. 总量（token/月）
2. 周量（token/周）
3. 其中 **lead 那部分** —— 这才是真正的天花板；sidekick 免费只是把同一笔额度摊薄。

再补一句「这个数对缓存率极敏感，跑一次 `/session-stats` 能看到自己的真实配比」。

## 常见错误

- 拿月费当额度（$200 的档通常给 $1,000–1,500 的 API 等值，比例会变）。
- 把促销价当常态，或忘了 cache write 按 1.25×/2× input 计费。
- 用「每任务成本」代替「每 token 成本」：两者的排序可以相反，成本低的那对可能只是任务跑得更碎。
- 只看总量不看周量：周额度是硬约束，月量再大也救不了周一就撞墙。
- 把数据集的旧快照当现值：先找最近的实测锚点对一遍，差一倍就说明额度被调过。
