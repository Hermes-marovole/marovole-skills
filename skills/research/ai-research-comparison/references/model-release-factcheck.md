# 新模型发布首日的事实核验与榜单口径审计

触发：用户说「X 发布了，你做个调研」，或目标模型上线不到 72 小时。此时官方博客、模型卡、技术报告常常还没有，网上的数字一半来自快讯转载，一半来自单人早期内测。这份手册规定「先验什么、冲突时信谁、榜单怎么读」。

## 1. 五路实时探针（先跑，再谈结论）

论坛与新闻稿都不算证据；能实时返回的接口才是。同一轮里打完这五路，把结果落进 scratch 的事实矩阵。

| 探针 | 取什么 | 判读 |
| --- | --- | --- |
| `GET <base>/v1/models`（**订阅端点与通用端点各打一次**） | 模型 id 是否在列表 | 只在订阅端点出现 = 仅订阅可用；两个都出现 = 接口层已铺开，但按量价目表可能还没挂 |
| `https://models.dev/api.json` | `context` / `output` / `attachment`（视觉）/ `reasoning` / `open_weights` | 这是第三方镜像的 mtime 级事实，比媒体快讯可靠，但仍是镜像，与官方文档冲突时以后者为准（官方若已发） |
| `https://openrouter.ai/api/v1/models` | 是否已有路由条目 | 未收录 ≠ 不能用，只说明开源路由/第三方托管还没接 |
| `docs.<domain>/llms.txt` 与官方 blog / model card URL | 文末版本号、HTTP 状态码 | `llms.txt` 停在上一代、blog 与 model card 返回 404，就是「文档滞后于接口」的硬证据，必须写进报告而不是含糊说「官方暂无消息」 |
| HF 组织页（`huggingface.co/<org>`） | 有无该版本仓库 | 没有仓库就是没开权重，别用榜单分类推断 |

**冲突时的信任序**：接口实际返回 > 官方文档/模型卡 > `models.dev` 这类实时镜像 > 控制台 UI 标签 > 媒体报道。媒体报道的错误很具体：上下文窗口被写错一个量级（把 1M 写成 20 万）、把上一代的最大输出沿用给新一代。写报告时把这处冲突单独列一条「已澄清」，比默默用正确值更有说服力。

## 2. 第三方聚合站的价格是占位信号的识别法

新模型上架聚合站时，页面常先挂一个远低于上一代的价格。两条判据同时命中就判为占位，不得进入年度预算测算：

- 页面对该模型注明能力标签「未公布 / not published」；
- 页面上同时挂着一个标「Coming Soon」的下一代模型，标价与它**完全一致**。

遇到占位价，成本测算退回上一代官方按量价（美元与人民币两套都列），并写明「官方价未发布，此处为对照情景」。

## 3. 榜单口径审计四问

刚发布的模型，唯一的成体系评测往往来自一两个博主的早期内测榜。转发它的标题分之前逐条问完：

1. **分是谁打的？** 自评、对手模型评、人工评混合很常见。评分者名单要写进表注，不能只写分数。
2. **提示词重跑过没有？** 「澄清提示词后重跑」会把分数抬高，而榜单标题用的是重跑分、脚注里还留着同提示词分。两个分都要进表（如标题 33.2 / 同提示词 31.8），并说明差值从哪来。
3. **带 `*` / `†` 的行是什么？** 通常是「由另一模型重新评分」或「沿用旧榜部分产物（partial artifact）」，不改分数但改变可比性。
4. **是不是 NDA 预览？** 图上标 `Internal only (NDA)`、项目数只有个位数，就在表注里写明这是正式报告前的早期预览，不当作行业共识。

同一张表里，代际提升（对上一代净增多少分）通常比绝对名次更稳：绝对名次受对手阵容变化影响，净增分只依赖同一个评测口径。

## 4. 「#1 Open Model」「开源」「全面开源」这类字样要回仓库验，而且按模型逐个验

榜单分栏、新闻标题、发布会 PPT 里的「开源 / Open」是营销标签，不是仓库事实。检查点：`models.dev` 的 `open_weights` 字段、HF 组织下有无对应仓库、OpenRouter 有无路由、ModelScope 镜像是否存在。任一处缺，就写「榜单归入开源阵营，但权重与路由均未见」。

### 4.1 一次发一整个模型家族时，先做「交付物矩阵」

厂商一次发布会常放 4–6 个模型，媒体统一写成「全面开源」，实际是分批、分层交付。逐个仓库打开后，公告里的模型会落进五种桶，五种桶在报告里必须是五句不同的话：

| 桶 | 仓库里实际有什么 | 报告写法 |
| --- | --- | --- |
| 完整权重 | HF/ModelScope safetensors + config + 推理配方，`license` 明确、`gated=false` | 「已开源权重（协议 X，无门控）」+ 指向推理配方 |
| 量化 / 衍生权重 | 基于上一行的 RTN 等量化版本，体积更小但**上下文常被缩水** | 单独一行，写明「量化版上下文短于源模型」（1M → 262K 这类缩水必须写出来） |
| 只发编码器 | 权重是千万参数级小模型，卡片明写 `task-specific prediction heads are not included` | 「只开源表征层，宣称的下游能力不可开箱用」——别把宣传里的能力数当成交付 |
| 只发代码 + 评测集 | GitHub 代码 + JSONL 评测集 + arXiv 技术报告，权重挂在厂商 API 后面 | 「可复现评测、不可自托管」，并点明引入该模型 = 引入厂商 API 依赖 |
| 全闭源 | 无仓库、无模型卡、无 API 文档，只存在于自家 App | 「无公开产物」，不要因为它出现在发布会上就当成可用组件 |

判读要领：**越靠近临床决策与风险判定的组件，交付得越少**（风险预测头、安全护栏权重留在内部或只在 API 后面）。这是从产物反推的结论，报告里必须标「属推断，厂商未说明理由」——厂商不会替你说这句话，而读者会把推断当公告。

### 4.2 硬件门槛读推理配方，不读宣传语

「可在笔记本上部署」与模型卡里的推荐启动命令经常差一个数量级：卡片给的 `--tp 4/8` 加 GPU 型号才是事实（4×141GB 级、8×80GB H100/H800 这类）。写「本地可部署」之前，把 SGLang / vLLM 那段命令里的并行度 × 显存算一遍，并区分「能跑」（量化版 + 小 batch）与「推荐配置」。

### 4.3 「SOTA」「第一」要落到具体榜单与具体口径

同一份发布通常有两套数字：自家 16 项基准图，和一个第三方综合指数。两套都写，各自带口径：

- **自家图表**：用 `vision_analyze` 直接读模型卡内嵌的评测图，逐格取数。媒体转述会漏掉「这一项我们落后 14 分」的对照栏；图里每个 benchmark 的值域不同（0–100 与百分比混排），抄进同一张表前统一标量纲。
- **第三方综合指数**：先查它的权重与覆盖面再引用。「综合第 N」和「开源第 1」是两个格子；指数只覆盖评测矩阵少数几格时（例如三行三列只测了三格、患者/公众那一列全空），必须在表注写明覆盖缺口，否则读者会把它当全景排名。
- **名次看完整榜单文件**（GitHub README 的 news 行、论文 Table），不要只引厂商挑出来的那一行。

### 4.4 限免 API 是最便宜的实测入口

厂商标配的自家 MaaS 模型页同时给：单价（限免常写 ¥0/M）、上下文、P50 吞吐 / TTFT / 可用率、调用量趋势。把这一页写成「零成本先跑自家样本」的入口，并抄下免费期截止日——限免到期日往往就在发布会后几天，不写日期等于交付一个会过期的方案。

## 5. 慢与贵的归因顺序

新推理模型「慢」几乎总是被误写成 TPS 问题。先拆四个数：首字延迟、单步耗时、总步数、推理 token 总量。首字与单步正常而总耗时数倍于对手，原因就是步数与 token 膨胀；这时结论要写「不是吐字慢，是步数翻了几倍」，并配一组限时探针（同一批短任务在低档位能全过、高档位因思考超时掉分）证明档位行为倒挂。

## 6. 订阅额度变化的三种常见误读

- 「提升至 1.5 倍」= 变为原来的 1.5 倍（多 50%）；「提升 1.5 倍」= 变为 2.5 倍。照抄原文措辞，别自己换算。
- 老套餐常被排除在新额度之外（本身无周限额的早期档位），官方在用户群给的回复要引用原文，不能写成「全档提升」。
- 与第三方客户端绑定的「额外 N 倍限时活动」常在同一时间到期结束。看到额度上调，要同时查有没有别的加成被收回，否则会写出「净提升」的错误结论。

## 7. 机制与遥测分栏，不越界归因

发布方常在同一时间给出「新架构」（如循环/稀疏/混合专家）与「实测更慢、更烧 token」两个事实。在没有官方技术报告把两者连起来之前，把后者写成前者的必然结果是编造。写法：一段解释机制（引技术说明或业绩会原话，讲清它省的是什么——通常是存储与读取带宽，不是 FLOPs），一段陈述遥测（引实测记录），再明确一句「尚无报告说明两者关系」。
